# ADR-0002: Replace AgentAdapter with Microsoft Agent Framework agents

**Status:** Accepted  
**Date:** 2026-05-10

## Context

The harness uses an `AgentAdapter` ABC to isolate the eval pipeline from agent runtime details. Each adapter owns the tool-calling loop, instantiates its own Azure OpenAI client, and routes all tool calls through an injected `ToolSimulator`. A separate `manifest.yaml` carries tool definitions, thresholds, and category config. Phase 2 of onboarding generates a Python adapter stub with two `TODO` markers that an Adapter Author fills in.

This shape has three friction points:

1. **Parallel manifests.** The MAF declarative agent YAML and `manifest.yaml` carry overlapping information (tool names, descriptions, model config). Any future MAF-based deployment would require maintaining both in sync.
2. **Adapter boilerplate.** The generated adapter stub is 80% harness plumbing (client init, tool loop, trajectory recording) and 20% agent-specific logic. The Adapter Author role exists solely to fill that 20%.
3. **Closed runtime.** `AgentAdapter` cannot express MAF-native capabilities: graph-based multi-agent workflows, middleware pipelines, group collaboration, OpenTelemetry tracing. Adding them requires changing the ABC contract.

Microsoft Agent Framework (MAF) provides a production-grade Python agent runtime with declarative YAML agent definitions, a first-class middleware system, and Azure AI Foundry deployment integration. Its tool-calling loop, middleware pipeline, and agent manifest are all first-class framework concerns — not boilerplate the harness must generate.

## Decision

Replace `AgentAdapter`, `ToolSimulator`, and `manifest.yaml` with MAF agents and a harness-owned `StubToolMiddleware`. The change has five interlocking parts:

**1. Single MAF YAML as the authoritative agent artifact.**  
`cases/{agent}/agent.yaml` is a valid MAF declarative agent YAML extended with a `x-harness:` block carrying eval-specific metadata (categories, thresholds, persona references). One file is generated by `SpecInterpreter`, reviewed by the Architect, deployed to Foundry, and read by `EvalController`. `manifest.yaml` and adapter stubs are eliminated.

**2. Local MAF runtime for eval; Foundry for production.**  
`EvalController` loads the MAF YAML and runs the agent in-process using the MAF Python SDK. Stub middleware is injected before the run and removed after. The same `agent.yaml` is deployed to Azure AI Foundry for production with no changes — the `x-harness:` block is ignored by the MAF runtime.

**3. `StubToolMiddleware` replaces `ToolSimulator`.**  
A MAF middleware component intercepts tool dispatch before real tool function implementations execute. Before each case run, `EvalController` sets a `ContextVar` to the case's resolved `tool_responses` dict (inline values merged over fixture library lookups). The middleware reads the `ContextVar` and returns the scripted response without calling the real backend. After the run, `EvalController` reads the recorded trajectory from the middleware (pull model). The middleware is not registered in production Foundry deployments.

**4. Hybrid fixture library for tool response data.**  
Named tool response scenarios are stored in `stubs/{agent}/{tool_name}/` as YAML files and generated per-tool by `CaseGenerator` from the MAF YAML tool schemas. Test cases reference scenarios by name (`tool_responses: {search_available_slots: no_availability}`) or override inline for edge cases. Architects can review and edit the fixture library independently of test cases.

**5. Shared `personas/` library for domain personas.**  
Healthcare domain personas are defined once in `personas/` as typed YAML files and referenced by test case ID. Equity cases reference personas by ID rather than embedding demographics inline. The same persona exercises equity behavior consistently across multiple agents. `EvalController` upfront validation checks that all referenced persona IDs exist before the eval loop starts.

## Consequences

**What is eliminated:**
- `AgentAdapter` ABC and all concrete adapter implementations (`SchedulingAdapter`, `PriorAuthAdapter`)
- `ToolSimulator` and the `advance_turn()` call contract
- `manifest.yaml` as a separate artifact
- `AdapterScaffolder` and the two-`TODO` adapter stub
- The Adapter Author role — replaced by Tool Function Implementer (pure business logic, no harness boilerplate)

**What is unchanged:**
- `BaseScorer`, `Judge`, Category Registry — scoring pipeline is runtime-agnostic
- `EvalController` interface — still iterates cases, calls judge, collects results
- `CaseGenerator` behavior — reads tool schemas from MAF YAML instead of `manifest.yaml`
- `SpecInterpreter` purpose — now emits MAF YAML + triggers a deep LLM behavioral critique (Phase 2) before Architect approval
- Dashboard, PDF report, CI/CD exit codes

**New onboarding flow (3 phases):**
- Phase 1: `hls-eval onboard --spec` → LLM generates MAF YAML draft
- Phase 2: LLM deep-critiques the draft for behavioral completeness (missing error responses, ambiguous schemas, unsafe thresholds) → Architect reviews draft + critique together
- Phase 3: `hls-eval onboard --generate` → fixture library generated per tool, test cases generated referencing `personas/` and `stubs/`

**Trade-offs accepted:**
- `EvalController` now depends on the MAF Python SDK. Swapping to a different agent runtime in the future requires rewriting the eval driver, not just a new adapter class. Mitigated by the fact that MAF is the target production runtime — eval and production now use the same runtime, eliminating the class of bugs caused by adapter/runtime divergence.
- Tool trajectory is captured by harness middleware rather than by the adapter. If the MAF runtime changes its middleware API, `StubToolMiddleware` must be updated. This is preferred over maintaining a bespoke tool-calling loop in every adapter.
- The `x-harness:` extension block in the MAF YAML must be stripped or ignored before Foundry deployment. MAF ignores unknown extension fields by specification; no stripping step is required.
